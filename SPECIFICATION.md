# HACP Specification

Version: 0.1  
Status: Draft

## 1. Introduction

Human–AI Contribution Provenance (HACP) is a machine-readable format for describing how humans and generative AI systems contributed to a piece of content.

HACP does not attempt to infer provenance from the finished content.

Instead, provenance information is explicitly declared by the systems and people participating in the creation or publication process.

## 2. Basic document

A minimal HACP document looks like this:

```json
{
  "specVersion": "0.1",
  "origin": "human",
  "aiInvolvement": "assisted",
  "humanReviewed": true
}
```

## 3. `specVersion`

Required.

Defines the version of the HACP specification used by the manifest.

Example:

```json
{
  "specVersion": "0.1"
}
```

## 4. `origin`

Required.

Describes the primary intellectual origin of the content.

Allowed values:

| Value | Meaning |
|---|---|
| `human` | The primary intellectual origin is human |
| `mixed` | Human and AI contributions are substantial |
| `ai` | The primary content was generated by AI |

The `origin` field must not be interpreted as a quality assessment.

## 5. `aiInvolvement`

Required.

Describes the overall level of generative AI involvement.

### `none`

No generative AI was used in creating the content.

### `assisted`

AI acted primarily as a tool.

Examples:

- grammar correction,
- translation,
- restructuring,
- rewriting,
- formatting,
- summarization of human-provided material.

### `collaborative`

Human and AI both contributed substantially to the resulting content.

Examples:

- joint brainstorming,
- development of arguments,
- generation of examples,
- iterative drafting.

### `generated`

The majority of the resulting content was generated by an AI system.

## 6. `humanReviewed`

Optional.

Boolean value indicating whether a human reviewed the final content before publication.

```json
{
  "humanReviewed": true
}
```

This field represents an assertion by the manifest issuer.

It does not independently prove that the review occurred.

## 7. `contributions`

Optional.

Provides a more detailed description of human and AI contributions.

```json
{
  "contributions": {
    "human": [
      "concept",
      "expertise",
      "facts",
      "review"
    ],
    "ai": [
      "structure",
      "wording"
    ]
  }
}
```

Suggested human contribution types:

- `concept`
- `research`
- `expertise`
- `facts`
- `argument`
- `creative-direction`
- `drafting`
- `editing`
- `review`
- `approval`

Suggested AI contribution types:

- `brainstorming`
- `research-assistance`
- `structure`
- `drafting`
- `wording`
- `translation`
- `summarization`
- `editing`
- `generation`

The vocabulary may be extended in future versions.

## 8. `generator`

Optional.

Describes an AI system involved in producing or transforming the content.

```json
{
  "generator": {
    "provider": "OpenAI",
    "model": "GPT-5.6",
    "system": "ChatGPT",
    "requestId": "optional-provider-request-id"
  }
}
```

Implementations should avoid including personal information or sensitive prompt data.

## 9. Content binding

A provenance manifest may be bound to a specific piece of content using a cryptographic hash.

```json
{
  "content": {
    "hashAlgorithm": "sha256",
    "hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}
```

For text content, HACP 0.1 recommends:

1. UTF-8 encoding,
2. Unicode NFC normalization,
3. LF (`\n`) line endings,
4. no additional transformations before hashing.

The resulting bytes are hashed using SHA-256.

This intentionally makes the hash sensitive to content changes.

Future versions may define robust or transformation-resistant content identifiers.

## 10. Issuer

A manifest may specify the entity making the provenance claim.

```json
{
  "issuer": {
    "type": "publisher",
    "name": "Example Publishing"
  }
}
```

Suggested issuer types:

- `author`
- `publisher`
- `ai-provider`
- `platform`
- `editor`
- `tool`

## 11. Cryptographic signature

A manifest may contain or reference a cryptographic signature.

```json
{
  "signature": {
    "algorithm": "Ed25519",
    "keyId": "https://example.com/.well-known/hacp-key",
    "value": "BASE64_SIGNATURE"
  }
}
```

The signature allows a verifier to determine whether the signed provenance declaration was modified.

A valid signature proves that the holder of the corresponding private key signed the declaration.

It does **not** independently prove that every provenance claim is factually correct.

## 12. Multiple attestations

Future versions SHOULD support multiple parties attesting to different aspects of provenance.

For example:

```text
Author
  ↓
"I supplied the concept and facts."

AI Provider
  ↓
"This model generated the draft."

Publisher
  ↓
"A human editor reviewed and approved the article."
```

These attestations may provide a stronger provenance chain than a single declaration.

## 13. Web embedding

A website may expose a HACP manifest using JSON metadata.

```html
<script type="application/hacp+json">
{
  "specVersion": "0.1",
  "origin": "human",
  "aiInvolvement": "assisted",
  "humanReviewed": true
}
</script>
```

This mechanism is experimental.

Consumers MUST NOT assume that the presence of an unsigned manifest makes its claims trustworthy.

## 14. Privacy

HACP manifests SHOULD contain the minimum amount of information necessary to describe provenance.

Implementations SHOULD NOT expose:

- prompts,
- private conversations,
- personal identifiers,
- hidden system instructions,
- confidential source material.

## 15. Interpretation

A consumer of HACP metadata may use provenance information for purposes such as:

- transparency,
- content labeling,
- filtering,
- auditing,
- research,
- publishing workflows.

HACP itself does not define how content should be ranked, trusted or displayed.

## 16. Open questions

HACP 0.1 intentionally leaves several problems unresolved:

- How should edited content retain provenance?
- How should multiple AI systems be represented?
- How can provider attestations be standardized?
- Should contribution levels be quantitative?
- How should translations inherit provenance?
- How should partial document provenance work?
- How should cryptographic provenance interact with C2PA?
- Can statistical watermarks provide a fallback when metadata is lost?

These questions are expected to evolve through experimentation.
